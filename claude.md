# eCommerce Div Flow - MVP Full-Stack Specification

## Arquitectura del Proyecto
Este es un proyecto Full-Stack unificado en un solo repositorio utilizando Next.js 15 (App Router). Contiene tres capas integradas:
1. **Frontend Público (Tienda):** Rutas dinámicas para clientes finales.
2. **Dashboard de Administración:** Ruta protegida en `/admin` para la gestión del comercio.
3. **API Interna (API Routes):** Endpoints bajo `app/api/*` encargados de los CRUDs y la comunicación con la base de datos a través de Prisma ORM.

## Tecnologías Principales
- Framework: Next.js 15
- Lenguaje: TypeScript
- Base de Datos: PostgreSQL (Supabase/Neon) con Prisma ORM
- Autenticación: Auth.js v5 (Google Auth)

## Requisitos de Interfaz y Diseño (UI/UX)
- **Diseño Responsivo:** Toda la interfaz (tienda pública y panel de administración) debe ser 100% Mobile-First y adaptarse perfectamente a dispositivos móviles, tablets y pantallas de escritorio.
- **Tema Claro/Oscuro:** El proyecto debe soportar de forma nativa el cambio de tema (Light/Dark mode) utilizando las clases de Tailwind CSS y el sistema integrado en el repositorio base. Toda nueva vista debe heredar y respetar estos estilos.

## Reglas de Negocio Específicas del MVP
- **Single-Tenant:** El código se clona e implementa de forma independiente por cada cliente.
- **Flujo de Pago por WhatsApp:** No hay pasarelas de pago. El carrito de compras se procesa mediante un botón que abre un enlace de WhatsApp con un mensaje preformateado conteniendo el resumen del pedido.
- **Configuración de la Tienda:** El número de teléfono de WhatsApp de destino debe almacenarse en la base de datos y ser editable desde el Dashboard de administración.
- **Gestión de Imágenes:** Las imágenes se suben a un bucket público de Supabase Storage (`product-images`) desde el panel de admin y se guardan como URLs públicas de texto en el modelo. El framework Next.js debe configurar el dominio `*.supabase.co` en su archivo de configuración para permitir el renderizado nativo optimizado.
- **Exclusiones actuales:** Sin sistema de cupones ni control complejo de inventario.

## Esquema de Datos Requerido (Prisma)
Asegurar que los modelos reflejen los siguientes campos mínimos:
1. **Category:** id, name, slug, timestamps (CRUD completo en Admin).
2. **Product:** 
   - id, name, description, price
   - categoryId (Relación con Category)
   - images (Array de strings / URLs públicas de Supabase Storage)
   - marca (String)
   - modelo (String)
   - colores (String)
   - isActive (Boolean)
   - timestamps
3. **ConfiguracionTienda:** id, whatsappNumber (para control desde el Dashboard).
4. **Auth.js v5:** Modelos estándar (User, Account, Session) validados estrictamente contra la variable de entorno `ALLOWED_ADMIN_EMAIL` en el login.

## Requisitos Técnicos y de Experiencia (UX/DX)
- **Carga Eficiente de Imágenes:** El frontend debe utilizar el componente `<Image />` de Next.js con propiedades de aspecto (`aspect-ratio`) y layouts responsivos. Se prohíbe el uso de etiquetas `<img>` nativas.
- **Estados de Carga y Errores (Skeletons):** Cada interacción con la base de datos debe incluir un estado visual de carga utilizando Skeletons o Spinners atractivos, además de un manejo limpio de pantallas de error.
- **Validación de Formularios Extrema:** El formulario de creación/edición de productos en el Admin debe validar que los enlaces de imagen (Supabase Storage) sean URLs válidas, que el precio sea mayor a cero y que los campos obligatorios no se envíen vacíos.
- **Preparación para Producción (Build Clean):** Todo el código de TypeScript debe estar estrictamente tipado. No se permite el uso de `any` para garantizar que el despliegue en Vercel pase el comando `npm run build` sin errores en el primer intento.
- **Manejo de Moneda y Formato:** Todos los precios mostrados en la tienda y el administrador deben formatearse dinámicamente según la moneda local requerida mediante `Intl.NumberFormat` de manera centralizada.


## Decisiones de Implementación (para no generar ambigüedad)
- **Rutas de Producto:** `Product` no tiene `slug` (solo `Category` lo tiene). Las rutas públicas de producto son `/products/[id]`, no `/products/[slug]`.
- **API Routes vs lecturas directas:** Las mutaciones (crear/editar/borrar) del Admin pasan por `app/api/admin/*`. Las lecturas para renderizar páginas (Server Components) consultan Prisma directamente vía `server/queries/*`, sin pasar por una API Route intermedia, para evitar una vuelta de red innecesaria dentro del propio servidor.
- **Tema Claro/Oscuro:** Implementado con `next-themes` (`ThemeProvider` en `app/layout.tsx` + `<ThemeToggle />` en el header público y en el panel admin). Las variables de color ya estaban definidas en `styles/globals.css` (`:root` y `.dark`), solo faltaba conectar el toggle.
- **Auth.js v5 real:** Dos providers en `lib/auth.ts`: Google (gate por `ALLOWED_ADMIN_EMAIL`) y un `CredentialsProvider` de cuenta de prueba (`TEST_ADMIN_USER`/`TEST_ADMIN_PASS` en `.env`) para que terceros prueben el panel sin Google. Ambos dan acceso completo, sin roles ni tabla de permisos — si existe sesión, es admin. El callback `signIn` aprueba directo cuando `account.provider === 'credentials'` (ya validado en `authorize()`) y valida el email solo para Google. `middleware.ts` protege `/admin/*` y `/api/admin/*` igual que antes.
- **Base clonada vs. MVP real:** El repo base (`SatvikPraveen/Nextjs-Ecommerce`) traía Stripe, `Cart`/`CartItem`/`Order`/`OrderItem`/`Review`/`Newsletter`/`Inventory`/`ProductVariant` en el schema, cuentas de cliente con perfil/historial de pedidos, y un uploader a S3. Todo eso se eliminó por completo (código y modelos) porque no aplica a este MVP (pago por WhatsApp, sin cuentas de cliente, imágenes solo por URL de Supabase Storage). Si aparece algo que referencie esos conceptos, es código viejo que no debería haber sobrevivido — bórralo, no lo repares.
- **Imágenes vía Supabase Storage:** `lib/supabase-admin.ts` crea un cliente admin (`SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY`, Service Role Key server-only, nunca expuesta al cliente) apuntando al bucket público `product-images`. `app/api/admin/upload/route.ts` (protegida por `middleware.ts` al vivir bajo `/api/admin/*`) recibe los archivos por `FormData`, los sube al bucket y devuelve las URLs públicas. `components/admin/image-upload-button.tsx` es el único punto de entrada en el Admin para subir imágenes (reemplazó a un uploader de Cloudinary que ya no existe) y se usa tanto en `product-manager.tsx` como en `banner-manager.tsx`. `next.config.mjs` restringe `remotePatterns` a `*.supabase.co` (antes `res.cloudinary.com`). Se agregó `loremflickr.com` a esa lista únicamente para las imágenes de prueba de `prisma/seed.ts` (fotos reales de Flickr con licencia CC, filtradas por keyword según la subcategoría — no paisajes aleatorios) — quitar ese host antes de producción con un cliente real.
- **Home con carruseles:** `app/page.tsx` arma tres bloques: `Banner` (modelo nuevo, CRUD en `/admin/banners`, carrusel full-width con autoplay), "Los más vistos" (`Product.views`, incrementado en cada visita a `/products/[id]` vía `incrementProductViews`) y un carrusel por cada categoría con productos activos. El carrusel base es `components/ui/carousel.tsx` (wrapper de `embla-carousel-react`, patrón shadcn/ui), reutilizado por `components/product-carousel.tsx` y `components/home/banner-carousel.tsx`.
- **Modelo `Banner`:** `id, imageUrl, title?, subtitle?, linkUrl?, order, isActive, timestamps`. CRUD completo en `/admin/banners` (mismo patrón que Category/Product: Zod en `lib/validators.ts`, API en `app/api/admin/banners/*`, `AlertDialog` para borrar).
- **Subcategorías (`Category.parentId`):** `Category` tiene una relación autorreferencial (`parentId`/`parent`/`children`, relation `"CategoryHierarchy"`) limitada a **un solo nivel**: una categoría con `parentId` es subcategoría, una categoría sin `parentId` es principal; una subcategoría no puede a su vez tener hijas (validado en `app/api/admin/categories/route.ts` y `[id]/route.ts`, no a nivel de base de datos). `Product` tiene `categoryId` (obligatoria, siempre la categoría principal) y `subCategoryId` (opcional; si se define, debe ser hija directa de `categoryId`, validado en `app/api/admin/products/route.ts` y `[id]/route.ts`). `server/queries/products.ts#getProductsByCategorySlug` acepta el slug de una categoría principal o de una subcategoría y busca productos por `categoryId` **o** `subCategoryId` para que ambas vistas funcionen. El dropdown "Categorías" del navbar (`components/categories-menu.tsx`) solo lista categorías principales (`parentId: null`), máximo 10 + "Ver más" hacia `/categories`.
- **Chrome condicional (Header/Footer):** `app/layout.tsx` es el único root layout (Next.js App Router no permite múltiples roots sin reestructurar todo en route groups). Para que `/admin/*` y `/auth/signin` no muestren el Header/Footer públicos, `components/site-chrome.tsx` (Client Component, usa `usePathname`) los oculta condicionalmente; `Header`/`Footer` se pasan ya renderizados como props (`header`/`footer`) desde `app/layout.tsx` porque un Client Component no puede importar y renderizar directamente un Server Component que usa `auth()`/Prisma.
- **`Header` es Server Component:** `components/header.tsx` ya no lleva `'use client'` — necesita `auth()` (para el botón "Panel admin", visible si hay sesión) y `getTopLevelCategories()` (para el dropdown). Los subcomponentes interactivos (`CartDrawer`, `ThemeToggle`, `CategoriesMenu`) siguen siendo Client Components renderizados desde él.
- **Formulario de asesoría:** `app/(store)/contacto/page.tsx` + `components/contact-form.tsx` envían el formulario a `app/api/contact/route.ts`, que usa `lib/mailer.ts` (Nodemailer + SMTP, variables `SMTP_HOST/PORT/USER/PASS` y `CONTACT_EMAIL_TO` en `.env`) para reenviar el mensaje por correo. No se guarda en base de datos (no hay modelo `ContactMessage`, por simplicidad del MVP).
- **Login de prueba en UI:** `app/auth/signin/page.tsx` usa `components/icons/google-icon.tsx` (SVG oficial a color) en el botón de Google y `components/ui/password-input.tsx` (con ícono de ojo de `lucide-react`) en el campo de contraseña de la cuenta de prueba.
- **Vista de detalle de producto enriquecida:** `app/(store)/products/[id]/page.tsx` renderiza explícitamente todos los campos de `Product` (incluidos `marca` y `modelo`, bajo esas mismas etiquetas). Incluye `components/trust-badges.tsx` (bloque estático de confianza: asesoría técnica, compra segura, entrega por WhatsApp) y `components/share-buttons.tsx` (WhatsApp, Facebook, copiar enlace).
- **`marca`/`modelo` (antes `campoTexto1`/`campoNumero2`):** nombres genéricos del MVP inicial, renombrados a su uso real ahora que el catálogo de prueba dejó claro para qué servían. `modelo` cambió de `Float` a `String` (es texto libre como "Galaxy S23", no un número) — por eso en `product-manager.tsx` el input de modelo dejó de ser `type="number"`.
- **Herramienta de precios masivos:** `/admin/bulk-pricing` (`app/admin/bulk-pricing/page.tsx` + `components/admin/bulk-pricing-form.tsx`) permite subir/bajar precios de muchos productos a la vez. Alcance mutuamente excluyente: por categoría/subcategoría, selección manual (tabla con checkboxes y buscador) o catálogo completo. Ajuste por porcentaje o monto fijo (con signo para subir/bajar). `lib/validators.ts#bulkPricingSchema` valida el payload con `.refine()` condicionales; `app/api/admin/bulk-pricing/route.ts` (PATCH) recalcula y actualiza en una sola `prisma.$transaction`, con precio mínimo forzado a `0.01`.
- **Colores de producto vía `colores` (antes `campoTextoGeneral`):** no existe un modelo real de variantes (por diseño, ver "Exclusiones actuales"). El campo `colores` (originalmente un nombre genérico de specs técnicas, en desuso real, renombrado para ser autodescriptivo) guarda los colores como texto serializado `"Nombre:#hex,Nombre:#hex"` (`lib/product-colors.ts#parseProductColors/serializeProductColors`). Es **opcional** — por eso `productSchema.colores` en `lib/validators.ts` no exige `min(1)`, solo `.default('')`; un producto sin colores guarda `""`. En el Admin, `components/admin/product-color-editor.tsx` reemplaza el input de texto por un editor de chips (nombre + `<input type="color">` + agregar/quitar). En la tienda, `components/product-color-swatches.tsx` recibe la lista ya parseada (`parseProductColors(product.colores)` hecho en la propia page, Server Component) y no renderiza nada si el producto no tiene colores. El antiguo `Accordion` de "especificaciones técnicas" se eliminó junto con `components/ui/accordion.tsx` y la dependencia `@radix-ui/react-accordion` (sin otro uso en el proyecto).
- **Carga de imágenes sin URLs manuales:** `components/admin/image-dropzone.tsx` reemplazó a `image-upload-button.tsx` (borrado, sin otro uso) en `product-manager.tsx` y `banner-manager.tsx`. Es un dropzone real (arrastrar/soltar o clic) que sube directo a `/api/admin/upload`; al terminar, muestra la previsualización con botones de copiar enlace y quitar. El usuario ya no ve ni pega ningún campo de texto con una URL — `Product.images` en el formulario se maneja como `string[]` directo en el estado (ya no como texto con URLs separadas por línea).
- **Campos obligatorios marcados en el Admin:** `components/ui/required-mark.tsx` (asterisco rojo) se agrega junto al `<Label>` de cada campo que el schema de Zod correspondiente exige de verdad (en `product-manager.tsx`: Nombre, Precio, Categoría, Marca, Modelo; en `category-manager.tsx`: Nombre, Slug). Si cambia una regla de `lib/validators.ts`, hay que revisar si el asterisco del campo asociado sigue siendo correcto.
- **JSON-LD en detalle de producto:** `app/(store)/products/[id]/page.tsx` inyecta datos estructurados `Product`/`Offer` (tipados con `schema-dts`, ya estaba instalado) vía `<script type="application/ld+json">`. La disponibilidad del `Offer` (`InStock`/`OutOfStock`) se deriva de `product.isOutOfStock`.
- **Producto agotado (`Product.isOutOfStock`):** flag booleano independiente de `isActive` — **no es control de inventario** (sigue prohibido por "Exclusiones actuales"), solo indica visualmente que no hay unidades sin ocultar el producto del catálogo/SEO. Se marca desde un checkbox en `product-manager.tsx` (con badge "Agotado" en la tabla). En la tienda, `product-card.tsx` y la página de detalle muestran el badge/mensaje y deshabilitan `<AddToCart>`; el producto sigue siendo indexable y visible.
- **"Vistos recientemente":** mismo patrón que la wishlist (Context + localStorage, sin backend). `components/recently-viewed-provider.tsx` (`RecentlyViewedProvider`, clave `'recently-viewed'`, máximo 12, dedupe+prepend) montado en `app/layout.tsx`. `components/track-recently-viewed.tsx` (Client, `useEffect` sin UI) registra la visita desde la página de detalle; `components/recently-viewed-carousel.tsx` lee el contexto, excluye el producto actual y reutiliza `ProductCarousel`.
- **Paginación y filtros server-side en listados públicos:** `/products`, `/category/[slug]` y `/search` reemplazaron el filtrado 100% en cliente (antiguo `components/product-toolbar.tsx`, borrado) por lectura de `searchParams` + queries Prisma con `skip`/`take`. `server/queries/products.ts` centraliza esto: `ProductListFilters` (sort, rango de precio, categoría/subcategoría, page/pageSize) y `PaginatedProducts` como contrato común de `getActiveProducts`, `getProductsByCategorySlug` y `searchProducts` (todas devuelven `{products, totalCount, totalPages, page, pageSize}`, `DEFAULT_PRODUCT_PAGE_SIZE = 12`). `components/product-filters.tsx` (Client, `useSearchParams`/`router.push`) y `components/pagination.tsx` (Client) manipulan la URL; toda página que los use debe envolverlos en `<Suspense>`. En `/category/[slug]` no se pasa la prop `categories` a `ProductFilters` (la categoría ya la fija la ruta). `Pagination` renderiza `<Button>` deshabilitado (no `Link`) en los límites, porque el atributo HTML `disabled` no bloquea un `<a>`.
- **Leads (intención de compra):** modelo `Lead` (`id, items: Json, totalAmount, createdAt`) registra un snapshot del carrito **antes** de abrir WhatsApp, sin pedir datos adicionales del cliente ni bloquear/reemplazar el flujo existente. `components/cart-checkout.tsx#logLead` hace un `fetch` fire-and-forget a `app/api/leads/route.ts` (POST público, valida con `lib/validators.ts#leadSchema`) en el `onClick` del link de WhatsApp; si falla, el cliente igual llega a WhatsApp. `server/queries/leads.ts` expone `getLeads` (paginado) y `getLeadStats` (total, potencial de ventas via `_sum`, leads hoy/semana, top 5 productos más cotizados agregado en JS sobre los últimos 200 leads).
- **Panel admin de Leads:** `/admin/leads` (`app/admin/leads/page.tsx`) muestra las stat cards de `getLeadStats`, el ranking de productos más cotizados y la tabla paginada de `getLeads`. Entrada "Leads" agregada a `components/admin/admin-sidebar-nav.tsx`. El dashboard principal (`app/admin/page.tsx`) suma dos stat cards ("Leads (hoy)", "Potencial de ventas") que enlazan a `/admin/leads`.
- **PWA sin dependencias:** `app/manifest.ts` (Metadata API de Next.js, se sirve solo en `/manifest.webmanifest` sin necesidad de `<link>` manual) usa `STORE_CONFIG.identity` y los íconos `public/icons/icon-192.png`/`icon-512.png`. `public/sw.js` es un service worker escrito a mano (sin Workbox): cache-first para imágenes, network-first con fallback a caché para navegación, y bypass total (sin interceptar) para `/admin`, `/api` y `/auth` para no cachear datos privados/dinámicos. `components/pwa-register.tsx` (Client, sin UI) lo registra desde `app/layout.tsx`.
  - **Fix: el fallback de navegación mentía sobre qué página se estaba mostrando.** Versión anterior (`v1`): si `fetch(request)` fallaba (sin red, o cualquier error de red) y la ruta pedida no estaba cacheada exacta, hacía `caches.match('/')` a ciegas -- servía el Home cacheado para CUALQUIER ruta, así que un usuario en `/cart` sin red veía el contenido del Home con la URL todavía diciendo `/cart`. Detectado en vivo durante testing (una extensión de VPN del navegador de prueba rompía `fetch` hacia `localhost`, lo cual expuso el bug, pero el bug en sí es real independientemente de la causa de red). Fix (`v2`, bump de `CACHE_NAME` para forzar la actualización del SW en el próximo visit): el catch ahora solo sirve caché si es un match EXACTO de la request (`caches.match(request)`, sin `ignoreSearch`); si no existe, responde con `OFFLINE_HTML` (string inline en el propio `sw.js`, sin depender de `STORE_CONFIG` ni de ningún import -- este archivo no pasa por el build de Next.js/webpack) en vez de adivinar con el Home. Mentir sobre qué página es es peor que avisar honestamente que no hay conexión.
- **Selector de país en el número de WhatsApp:** `components/admin/phone-number-input.tsx` reemplaza el `<Input>` de texto plano en la configuración de WhatsApp por un `Select` con bandera + código de marcado automático (`lib/countries.ts`, 23 países foco Hispanoamérica, sin ninguna librería externa — la bandera es un emoji Unicode). `splitWhatsappNumber()` reconstruye país + número local a partir del string guardado. El contrato de datos no cambió: sigue emitiendo/recibiendo el mismo string "solo dígitos" (código + local pegados) que ya exigían `configuracionTiendaSchema` (`lib/validators.ts`) y `lib/whatsapp.ts` — el componente es puramente de UX, cero cambios de schema/API.
- **`/admin/settings` y `/admin/announcement-bar` son páginas separadas:** aunque ambas leen/escriben el mismo singleton `ConfiguracionTienda`, viven en pantallas distintas a propósito. `/admin/settings` (`components/admin/whatsapp-settings-form.tsx`) es exclusivamente "Verificar número de WhatsApp" — incluye un card `Próximamente` (deshabilitado, solo visual) reservando el espacio para verificación de correo/WhatsApp e integraciones futuras, para que esa sección crezca sin mezclarse con contenido de banner. `/admin/announcement-bar` (`components/admin/banner-settings-form.tsx`) es solo el banner de anuncios, con vista previa full-bleed (`-mx-6` dentro del `CardContent`) idéntica a `components/announcement-bar.tsx`. Cada formulario reenvía los campos de la *otra* pantalla tal cual los recibió por props (`initialConfig`) al hacer `PATCH /api/admin/settings`, para no pisar el campo que no le corresponde — la API y el validador Zod no cambiaron, siguen esperando los 3 campos juntos. Nav items en `components/admin/admin-sidebar-nav.tsx`: "Verificar número de WhatsApp" seguido de "Banner de la tienda".
- **Favicon vía convención de archivos de Next.js:** `app/icon.png` (256×256, favicon de pestaña) y `app/apple-icon.png` (180×180, ícono al agregar a inicio en iOS/Safari) — Next.js los detecta solo y genera los `<link rel="icon">`/`<link rel="apple-touch-icon">` correspondientes, sin tocar `metadata` en `app/layout.tsx`. Mismo tratamiento visual que los íconos de PWA: fondo blanco sólido + logo (`logodark.png`) centrado al 70% sobre lienzo cuadrado, para que se vea bien en pestañas/accesos directos sin depender del tema claro/oscuro del navegador. Al adaptar el proyecto a un cliente nuevo, se reemplazan ambos archivos igual que `logolight.png`/`logodark.png` — no son datos de `store-config.ts`, son assets. Distinto de `public/icons/icon-192.png`/`icon-512.png`, que siguen existiendo aparte porque cumplen un rol distinto: los íconos que exige el manifest de la PWA (`app/manifest.ts`) para "Agregar a pantalla de inicio".
- **`lib/store-config.ts` — datos planos de cliente, sin lógica:** dado que el proyecto es single-tenant (se clona por cliente), este archivo es lo único que hay que llenar a mano al integrar un cliente nuevo. Es un objeto plano en español, sin interfaces técnicas ni comentarios de wiring a componentes: `nombre`, `slogan`, `descripcion`, tres colores de marca en hexadecimal (`colorPrimario/colorSecundario/colorAcento`, un solo valor cada uno — no se pide versión clara/oscura, ver más abajo por qué), contacto/redes planos (`correoSoporte/telefono/direccion/instagram/tiktok/facebook`, todos string vacío por defecto) y flags booleanos (`mostrarBannerAnuncios/mostrarFavoritos/mostrarVistosRecientemente/mostrarColoresDeProducto`). Deliberadamente **no** incluye `whatsappNumber`/`bannerText`/`showBanner` (dato operativo en `ConfiguracionTienda`, editable día a día desde `/admin/settings` y `/admin/announcement-bar`) ni el logo (no es un campo de texto: se reemplazan directo los archivos `public/images/logolight.png`/`logodark.png`) ni flags de módulos que no existen (ej. reseñas, excluido por "Exclusiones actuales" del MVP). Cada componente que lee un flag lo hace directo (`STORE_CONFIG.mostrarFavoritos`, etc.) — la lógica de qué controla cada flag vive en el componente que lo consume, no en el archivo de config.
- **Colores dinámicos: hex de cliente → HSL de Tailwind, con contraste automático:** `lib/theme.ts` es donde vive toda la lógica técnica que `store-config.ts` ya no tiene. `hexToHsl()` convierte cada color hex a `"H S% L%"` (formato que ya usan las variables de `styles/globals.css`, así `tailwind.config.ts` sigue funcionando sin cambios). `readableForeground()` calcula solo (fórmula de luminancia YIQ) si el texto sobre ese color debe ser casi-negro o casi-blanco, para no tener que pedirle al cliente un color de texto combinado. `generateThemeStyleTag()` arma `:root{...} .dark{...}` con `--primary/--secondary/--accent` (+ sus `-foreground`) y se inyecta con `<style dangerouslySetInnerHTML>` en un `<head>` agregado a mano en `app/layout.tsx` (soportado por Next.js App Router para tags no cubiertos por la Metadata API); gana por cascada al declararse después de `globals.css`, sin `!important`. El mismo color se usa en `:root` y en `.dark` a propósito: el color de marca no cambia con el tema, solo el fondo de la página (ya resuelto por el toggle de tema existente). Los neutros estructurales (`background`, `foreground`, `card`, `border`, `input`, `ring`, `muted`, `destructive`) se quedan fijos en `globals.css`: no son identidad de marca, son parte del sistema de diseño base y dependen del modo claro/oscuro, no del cliente.

- **Fix de build: `image-dropzone.tsx` no compilaba en Vercel (`noUncheckedIndexedAccess`).** El fix anterior de `uploadFiles` (ver fix de `/api/admin/upload` más arriba) hacía `data.urls[0]` después de chequear `data.urls.length === 0` -- pero `noUncheckedIndexedAccess: true` (`tsconfig.json`) no infiere esa garantía a partir de un chequeo de `.length`, así que `data.urls[0]` sigue tipando `string | undefined` y rompía el build (`next build` corre `tsc` real, a diferencia de `next dev`). Fix: desestructurar (`const [firstUrl] = newUrls`) y chequear `firstUrl` puntual antes de usarlo -- eso sí angosta el tipo a `string` dentro del bloque, sin recurrir a `as string`. Mismo patrón a seguir si aparece otro caso de índice sobre un array potencialmente vacío.
